# Delivery records

Business readers follow Tributary's progress through these records, on GitHub (`delivery/README.md`) and on the GitHub Pages site built from them. They are committed: every push updates what readers see, so a record is always true for the commit it is in.

| Record | Source | Who writes it |
| --- | --- | --- |
| Feature | `delivery/features/<task-id>.smd` | coder creates and keeps it current; harness marks it delivered |
| Release | `delivery/releases/<version>.smd` | release agent |
| Index | `delivery/README.md` and the `.md` beside each source | generated by `render`; never edited by hand |

Script: `node .claude/skills/delivery-docs/scripts/docs.mjs <command>` (exit 0 ok, 1 check failed, 2 error).

| Command | Does |
| --- | --- |
| `feature <task-id>` | Creates the feature record from the roadmap task. Does nothing if it exists |
| `progress <task-id>` | Ticked capabilities, "3 of 5 (60%)" |
| `list` | Every feature with its state and progress |
| `render` | Regenerates every `.md` copy and the index. Run it before each commit that touches a record |
| `check <task-id\|version>` | 0 smd errors, no `fill:` comments, at least one item, `.md` copies current |
| `finalize <task-id> --pr <url>` | Status approved ("Delivered") and the delivery line. The harness runs it after the QA pass |
| `release <version> --previous <v>` | Creates the release record listing delivered, unreleased features |
| `shipped <version>` | Release approved ("Released"); its features are marked with the version |
| `site <dir>` | Styled HTML pages and an index page; the Delivery pages workflow publishes them from `main` |

## Writing for business readers

- Say what people can do and why it matters. Class names, file names, commands and protocol details belong only in the collapsed Technical notes or Technical details section.
- A capability is an outcome someone can recognize: "Every pull request is checked for known vulnerabilities", not "Add codeql.yml". Each has an id, `{#<task-id>-<n>}`.
- Compatibility opens with one plain answer: "Nothing changes for existing users", or who is affected and what they must do.
- Rename the generated title to what the feature means for a reader ("T0A-11: Automatic quality checks on every change"). Keep the task id prefix.
- No claim without a source: tests, the compatibility report, CI and gate results.

## States

| smd `status` | Feature shows | Release shows | Set by |
| --- | --- | --- | --- |
| `draft` | In progress | In preparation | `feature` / `release` |
| `review` | In QA | Awaiting approval | coder at handoff / release agent at READY FOR APPROVAL |
| `approved` | Delivered (Released in X once shipped) | Released | harness `finalize` / `shipped` after the user's go |

Never set a state ahead of the fact, and never write a percentage by hand: progress is counted from the ticks.

## Rules

- Tick a capability in the same commit that completes it, once its tests pass, then `render`.
- Work found on the way that belongs to the task becomes a new capability; anything else becomes a non-goal naming the roadmap task it goes to. Nothing lands unlisted.
- A record finished for handoff has every capability ticked, or the unticked ones moved to non-goals with the reason, and `check` passes.
- The roadmap and other `docs/` files stay local (roadmap question Q10): records name the roadmap task but never link into `docs/`.
- The user approved publishing these records in the public repository. Nothing else from `docs/` goes with them.
